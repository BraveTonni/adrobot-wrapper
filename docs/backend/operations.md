# Эксплуатация

## Запуск

Локальный запуск backend и frontend через `make run` использует Docker Compose.
Секреты создаются командой `make secrets`, API-ключ Keitaro указывается
отдельно — см. [руководство по контейнерам](../containers.md).
Для прямого запуска процесса используйте переменные окружения или
`backend/.env`. В рабочей среде получайте ключ через менеджер секретов и не
храните его в репозитории.

Backend не стартует без `KEITARO_API_KEY`: сервис без ключа не может выполнить
ни одного запроса к Keitaro, и ошибка на старте понятнее, чем отказ каждого
запроса.

При запуске через Compose миграции выполняет сервис `migrate` после того, как
база проходит healthcheck. При прямом запуске процесса или в production
примените миграции отдельно:

```bash
cd backend
uv run alembic upgrade head
```

Затем запустите ASGI-приложение согласно окружению. Для локального запуска
используйте `make run`; в production следует запускать Uvicorn без `--reload`
и настроить количество workers согласно инфраструктуре.

## Проверка состояния

`GET /api/v1/health` выполняет `SELECT 1` в базе данных. Этот маршрут проверяет
доступность БД, но не проверяет соединение с Keitaro. Ошибки интеграции видны
по HTTP-статусу ответа и структурированным JSON-логам, куда попадает метод,
путь, статус и краткое тело ошибки Keitaro.

`GET /api/v1/operations` возвращает последние 50 операций: успешные изменения,
откаты и неудачные откаты кампаний.

Запись содержит действие, исполнителя (`X-User` или IP клиента), тип и ID
сущности, связанные ID кампании и потока, статус, detail, снимки до и после
изменения и текст ошибки. Запись `pending` фиксируется до мутации; завершение
сохраняет результат, а ошибка оставляет причину и соответствующий статус для
разбора.

Статусы создания кампании различают исход в Keitaro:

| Статус | Что произошло |
| --- | --- |
| `ok` | Кампания и потоки созданы |
| `failed` | Keitaro отклонил запрос или проверка не прошла до записи |
| `cancelled` | Клиент отключился до первого запроса на запись |
| `unknown` | Ответ на запрос создания не получен — кампания могла создаться |
| `rolled_back` | Создание не завершилось, кампания удалена из Keitaro |
| `rollback_failed` | Кампания осталась в Keitaro — нужна ручная проверка |

Записи `unknown` и `rollback_failed` — повод посмотреть кампанию в Keitaro и в
журнале: их ID сохранён в `detail`.

## Миграции и данные

При локальном запуске без контейнера SQLite создаёт файл `backend/adrobot.db`.
Для другой базы задайте `DATABASE_URL`. Миграции запускаются отдельно и при
старте приложения автоматически не применяются.

`uv run alembic check` сравнивает ORM-модели с применёнными миграциями и
заканчивается ошибкой, если они разошлись. CI делает это на PostgreSQL.

Backend поддерживает SQLite и PostgreSQL через `asyncpg`. Compose по умолчанию
поднимает PostgreSQL 16; SQLite остаётся вариантом для локального
однопроцессного запуска. Для PostgreSQL используйте TLS на соединении и
резервное копирование средствами провайдера базы.

Журнал операций и снимки кампаний не заменяют резервное копирование базы. План
резервного копирования выбирается для конкретной базы и среды развертывания.

## Ограничения

- Keitaro и локальная база не участвуют в общей транзакции. Перед удалённой
  мутацией создаётся запись `pending`; если её создать нельзя, операция не
  начинается. Ошибка финализации оставляет эту запись для ручной сверки.
- Изменения офферов отправляются полным списком. Между чтением потока и записью
  поток может изменить кто-то другой; в режиме черновиков публикация такое
  обнаруживает и отказывается, в прямом режиме окно равно одному запросу.
- Черновик потока общий для всех пользователей сервиса. Блокировки строк нет:
  одновременные правки одного черновика могут потерять одно из изменений.
- Счётчики rate limit и блокировки обновления кэша живут в памяти процесса; при
  нескольких workers они считаются независимо.

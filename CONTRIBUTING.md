# Руководство для участников

## Архитектурные принципы

- **SRP:** у каждого модуля одна причина для изменения. HTTP-контракты находятся
  в `backend/app/transport/http/schemas`, DTO Keitaro — в
  `backend/app/infrastructure/keitaro/schemas`, доменные сущности — в
  `backend/app/domain`, сценарии — в `backend/app/application`, ORM-модели — в
  `backend/app/infrastructure/persistence/models`.
- **DIP:** сценарии зависят от узких Protocol-портов; инфраструктурные
  репозитории реализуют их. Не добавляйте интерфейс только ради количества.
- **DRY:** выносите общее правило при реальном повторении; не объединяйте код с
  разным смыслом.
- **KISS и YAGNI:** выбирайте прямое решение и добавляйте абстракции только под
  существующую потребность.
- Держите константы рядом с единственным местом использования. Общий пакет
  констант нужен только значениям, которые используют несколько компонентов.
- Именуйте коммиты по Conventional Commits: `fix: reject an invalid offer
  response`, `test: cover campaign rollback behavior`.

## Требования к тестам: F.I.R.S.T.

- **Fast:** unit-тесты не обращаются к сети и внешним сервисам.
- **Independent:** тест не зависит от данных и порядка других тестов.
- **Repeatable:** результат одинаков при повторном запуске и в CI.
- **Self-validating:** pytest однозначно сообщает pass или fail.
- **Timely:** добавляйте тест одновременно с изменением поведения.

## Структура и читаемость тестов

- Используйте **Arrange — Act — Assert**: подготовка, вызов, проверка.
- Один тест проверяет один сценарий. Имя описывает условие и ожидаемое поведение.
- Проверяйте публичный результат и границы компонентов, а не приватные поля.
- Не используйте ветвления, циклы и сложные вычисления в тестах. Для простых
  наборов входов используйте параметризацию pytest.
- Выносите повторную подготовку в небольшие fixtures или фабрики, но не скрывайте
  Arrange за универсальными helper-объектами.
- Для каждого модуля с поведением держите отдельный тестовый модуль в папке
  соответствующего слоя. Пустые `__init__.py` и декларативные модули без
  исполняемого поведения отдельного unit-теста не требуют.
- Проверяйте ошибки на уровне слоя, который отвечает за их отображение.

## Локальные файлы

Разработческие заметки, фикстуры и другие временные файлы храните в `.local/`.
Git игнорирует содержимое этой папки, кроме `.gitkeep`.

## Проверки перед коммитом

Из корня репозитория запустите:

```bash
make fmt
make check
make test
```

`make fmt` сортирует импорты правилом Ruff `I` и форматирует Python-код.
GitHub Actions запускает `make fmt` и автоматически коммитит исправления.
`make check` — то же, что CI: Ruff, mypy strict, pytest, строгая сборка
документации и проверки frontend (ESLint, tsc, тесты, production build).
Отдельная джоба CI повторяет миграции и сценарии на PostgreSQL; после изменения
ORM-моделей убедитесь, что `uv run alembic check` не находит расхождений.
